# AGENTS.md — Loxtep SDK & CLI

Loxtep is **the Enterprise Context Layer**: the system that turns organizational
knowledge, expertise, and norms into machine-usable context for AI across
heterogeneous systems. You build and operate Loxtep **code-first** — from a
terminal and an editor — not by clicking through dashboards.

The primary surface is **CLI + SDK + MCP + skills + this doc**. The web UI is
reduced to user management, billing, and usage. If you are an AI coding agent,
everything you need to build on Loxtep is here.

> You can't unify fragmented systems with a fragmented system.

## The mental model: context as code

1. `loxtep login` — authenticate once (browser or console).
2. `loxtep init` — scaffold a workspace (`.loxtep/project.json` + `domains/`,
   `connectors/`, `workflows/`, `data-products/`).
3. `loxtep attach` — link the workspace to a Loxtep **Instance** (the same
   connection mechanism the web UI uses).
4. `loxtep generate` — compile every connected resource (data products,
   connectors, domains, queues, flows, workflows) into a single **typed** SDK
   artifact at `.loxtep/generated/index.ts`.
5. Author **data workflows as code** that reference real resources by name with
   compile-time safety.
6. `loxtep test` — run a workflow module locally and print its action trace.
7. `loxtep deploy` — compile modules into Loxtep's flow/workflow graph and deploy
   to the attached Instance.

The generated artifact is the contract: your agent builds against **ground truth**
(typed constants for the resources that actually exist) instead of guessing.

## Authentication (read this first)

**Every** Loxtep operation — CLI, SDK, and MCP — requires authentication. There
are no unauthenticated endpoints.

| Surface | How auth is provided |
| --- | --- |
| **CLI** | `loxtep login` stores credentials in `./.loxtep/credentials.json` (cwd; `--global` for `~/.loxtep/`). |
| **SDK** | `LOXTEP_AUTH_TOKEN` env var, or project-local then global `credentials.json`. |
| **MCP** | OAuth 2.1 + PKCE against `https://mcp.loxtep.io/ai/mcp/stream`. The browser flow runs on first connect; tokens refresh in the background. |

SDK auth precedence: `LOXTEP_AUTH_TOKEN` → `~/.loxtep/credentials.json`. When a
workspace exists, the SDK also auto-resolves `api_url`, `project_id`, and
`instance_id` from `.loxtep/project.json`.

## CLI reference (`loxtep`)

Installed with `@loxtep/sdk` (`pnpm exec loxtep <command>` or a global install). Run
`loxtep --help` for the live list — output is grouped by **customer-facing areas**
(Authentication, Workspace, Build & deploy, Governance, …). MCP facade names are
internal to the SDK and are not shown in CLI help.

### Lifecycle commands

| Command | What it does | Auth |
| --- | --- | --- |
| `loxtep login [--console]` | Authenticate. Browser by default; `--console` for email/password/TOTP. | n/a |
| `loxtep logout` | Remove stored credentials. | required |
| `loxtep whoami` | Print the current user and organization. | required |
| `loxtep init [--template <slug>]` | Scaffold a workspace; with `--template`, materialize the full template incl. `AGENTS.md` + a default skill. Prints Getting Started + Quick Reference links. | optional |
| `loxtep attach [--instance <id>]` | Link the workspace to an Instance; writes `instance_id` + `api_url` into `.loxtep/project.json`. | required |
| `loxtep generate` | Compile workspace context → `.loxtep/generated/index.ts`; validate skills; print per-type counts. | required + attached |
| `loxtep test <module> --event <file>` | Run one data workflow module locally against the attached Instance; print the action trace. | required + attached |
| `loxtep deploy` | Compile modules into the flow/workflow graph; deploy to the attached Instance. | required + attached |
| `loxtep activity list [filters]` | List unified activity + audit entries. | required |
| `loxtep improvements list \| apply <id> \| reject <id>` | Review and adopt AI-Eval-derived workflow improvements. | required |

### Ordering & exit-code contract

- Run `loxtep init` before `generate`/`test`/`deploy`; otherwise the CLI exits
  non-zero with "run `loxtep init` first".
- Run `loxtep attach` before `generate`/`test`/`deploy`; otherwise the CLI exits
  non-zero with "run `loxtep attach` first".
- `deploy` rejects atomically (no partial changes; previously deployed workflows
  keep running) on compile errors or references to resources that do not exist,
  printing each error with its file path and line number.

### Resource commands (always available after login)

```bash
loxtep data-products list
loxtep data-products get <id>
loxtep data-products create --name <n> --domain-id <uuid> --kind <source|consumer> [--description <text>]
loxtep data-products query <id> "SELECT * FROM t LIMIT 10"
loxtep data-products tables <id>

loxtep workflows list --project-id <id>
loxtep workflows get <id>
loxtep workflows create --name <n> --project-id <id> [--template-id <id>]
loxtep workflows deploy --project-id <id> [--instance-id <id>]

loxtep triggers list | get <id> | create --name <n> --type <type> --key <k> | test <id>
loxtep connectors  # (org-level connectors are managed via SDK/MCP)
loxtep domains list | get <id>
loxtep standards list | get <id>
loxtep data-contracts list | get <id>
loxtep queue info <data-product-id> | queue checkpoint <id> --bot <bot-id>
loxtep observe status
loxtep config list | paths | set <k> <v> | export --from-connector <id> [--format sh|json|env]
loxtep metrics rate-limits | log --id <id> --value <n>
```

## SDK reference (`@loxtep/sdk`)

### Client initialization

```typescript
import { LoxtepClient } from '@loxtep/sdk';

// Explicit config
const client = new LoxtepClient({
  api_url: process.env.LOXTEP_API_URL,
  organization_id: process.env.LOXTEP_ORGANIZATION_ID,
  project_id: process.env.LOXTEP_PROJECT_ID,
  instance_id: process.env.LOXTEP_INSTANCE_ID,
  region: process.env.LOXTEP_REGION,
  auth: { type: 'jwt', token: process.env.LOXTEP_AUTH_TOKEN! },
});

// Or auto-configure from the workspace (.loxtep/project.json + ~/.loxtep/credentials.json)
const fromWs = LoxtepClient.fromWorkspace();
```

### Client namespaces (v0.7+ MCP facades)

Since **v0.7.0**, `LoxtepClient` exposes **10 facades** that mirror hosted MCP
tools. Flat top-level namespaces (`client.data_products`, `client.workflows`, …)
are **removed**. See [`docs/sdk-mcp-mapping.md`](./docs/sdk-mcp-mapping.md).

| Facade | Nested APIs | Purpose |
| --- | --- | --- |
| `client.session` | — | Current user/org, logout |
| `client.connect` | `.connectors`, `.templates` | Connect external systems, templates |
| `client.workspace` | `.projects`, `.instances` | Projects, runtime instances |
| `client.build` | `.workflows`, `.triggers`, `.data_products`, `.targets` | Authoring, deploy, CRUD, stream/replay |
| `client.define` | `.schemas`, `.quality`, `.standards`, `.data_contracts`, `.domains` | Schema, quality, governance |
| `client.meaning` | `.thesaurus` | Vocabulary / ontology terms |
| `client.review` | `.approvals`, `.improvements` | HITL approvals, AI-eval improvements |
| `client.query` | `.catalog`, `.discovery`, `.query()`, `.list_tables()` | Discovery and analytics SQL |
| `client.observe` | `.status()`, `.stream_config()`, `.open_reader()`, … | Observe + low-level queue I/O |
| `client.context` | `.procedures`, `.activity`, `.process_intelligence` | Process intel, activity feed |

Top-level **`get_writer(name)`** / **`get_reader(name)`** resolve deployment
metadata for live stream I/O (preferred over calling nested APIs directly).

### Recommended write/read pattern

```typescript
// Resolve queue, bot_id, and stream config automatically from deployment metadata
const writer = await client.get_writer('orders_raw');
writer.write({ id: 'evt-1', payload: { sku: 'ABC', qty: 2 } });
await writer.close();

const reader = await client.get_reader('orders_raw');
for await (const event of reader) {
  console.log(event);
}
```

## MCP tool surface (hosted at `mcp.loxtep.io`)

The hosted MCP server exposes **10 MCP tools** aligned to Connect → Organize → Use.
Each call sets `operation` to the flat action name plus that action's arguments.
**Greenfield cutover:** deprecated names such as `loxtep_connectors`, `loxtep_workflows`,
or `loxtep_data_products` are **not** registered.

| MCP facade | SDK namespace |
| --- | --- |
| `loxtep_session` | `client.session` |
| `loxtep_connect` | `client.connect` |
| `loxtep_workspace` | `client.workspace` |
| `loxtep_build` | `client.build` |
| `loxtep_define` | `client.define` |
| `loxtep_meaning` | `client.meaning` |
| `loxtep_review` | `client.review` |
| `loxtep_query` | `client.query` |
| `loxtep_observe` | `client.observe` |
| `loxtep_context` | `client.context` |

Full operation tables: [`sdk-mcp-mapping.md`](docs/sdk-mcp-mapping.md) and
[loxtep-plugins-skills AGENTS.md](https://github.com/LoxtepInc/loxtep-plugins-skills/blob/main/AGENTS.md).

**Auth:** OAuth 2.1 + PKCE (all tools). **Scope:** `project` operations require
`project_id` in the same payload.

Add the server to any MCP client:

```json
{ "mcpServers": { "loxtep": { "url": "https://mcp.loxtep.io/ai/mcp/stream" } } }
```

Example (call tool **`loxtep_connect`**, not `loxtep_connectors`):

```json
{ "operation": "create_connector", "connector_type": "shopify", "metadata": { "api_key": "…" } }
```

## Hosting model (control plane / data plane)

`loxtep deploy` resolves the attached Instance type and targets accordingly:

| Instance type | Data plane runs in | Control plane (always Loxtep) |
| --- | --- | --- |
| `shared` / sandbox | Loxtep-operated infrastructure (free, multi-tenant) | auth, orchestration, triggers, scheduling, activity history, slim UI |
| `managed` | Loxtep-operated dedicated infrastructure (paid) | same as above |
| `self-hosted` | Your AWS account (cross-account role + BusInstall) | same as above |

`loxtep attach` links a project to any of these Instance types using the same
connection mechanism as the web UI.

## Skills (scoped agent access)

A **skill** declares which resources and operations an agent may reach inside a
workspace. Skill files live at `.loxtep/skills/<name>.yaml`. The MCP server
enforces scope **fail-closed**: out-of-scope resource access returns
`SCOPE_VIOLATION`, a disallowed operation returns an operation-denied error, an
unknown skill name is rejected, and if scope validation cannot complete the
operation is blocked. `loxtep generate` validates every skill reference against
the workspace context.

When invoking MCP tools, agents may pass `_metadata: { skill_name: '<slug>' }` for
attribution and eval scoring. It is optional and ignored for tool logic.
